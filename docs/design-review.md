# 《后室：无尽回廊》设计书评审报告

> 评审对象：设计书 v1.0（2026 版）
> 评审视角：可落地性（scope / 产能 / 技术 / 合规）
> 结论先行：**框架成立，方向正确，但"4000 层级"的产能模型、系统闭环、UGC 阶段与合规策略存在必须修正的硬伤。** 本报告按优先级列出问题与建议，修订结果见 `gdd-v0.2.md`。

## 一、做得对的地方（保留不动）

1. **"弱游戏性"定位**：明确拒绝任务-奖励循环，把交互性放在心理想象与审美层面。后室题材的恐怖恰恰来自"无目的性"。
2. **层级 DNA 抽象**：用参数化定义层级，是同时解决"规模"与"一致性"的正确抽象，方向完全正确（实现细节需修正，见 P0-2）。
3. **模块化资产库 + AI 辅助工作流**：三位一体方案本身成立，与现有独立开发实践（如 CoolPuzzler 的 Meshy 管线）一致。
4. **玩家自驱目标分类**：探索者/收藏家/生存狂/故事家/建筑师五类画像清晰，可直接转化为成就系统与内容投放策略。
5. **美学分层**：把"核类美学"（怪核/梦核/池核/伤核/商业核）作为层级的风格维度，成本低、辨识度高。

## 二、必须修正的核心问题

### P0-1 ｜ "4000 层级"的产能数学不成立

**现状**：设计书将 4000 层级（Fandom 常规至 Level 3999）作为发布目标，内容量产阶段仅 2-4 年、团队 7-9 人。

**产能测算**（按设计书自己的"层级 DNA + 模板"假设）：

| 工作项 | 单层成本（人日） | 4000 层总计（人日） |
|--------|----------------|--------------------|
| DNA 设计与平衡 | 0.5 | 2000 |
| 程序化参数调优 + 异常修复 | 1.0 | 4000 |
| 美学/光照/音频确认 | 0.5 | 2000 |
| 实体配置与安全验证 | 0.5 | 2000 |
| 出口图设计与回归测试 | 0.5 | 2000 |
| **合计** | **3.0** | **12000** |

12000 人日 ≈ **48 人年**。设计书的内容团队实际只有 2-3 名关卡设计师 + 1 名系统设计师 + 1 名技术美术，3 年产出约 **9-13 人年**，缺口 4 倍以上。即便把单层成本压到 1 人日，仍缺口 1.5 倍。

**结论**：**"发布即 4000 手作层级"在预算内不可能实现，且不该实现**——4000 层中大量是"废层"（Fandom wiki 本身也是大量 stub 页），玩家真正在意的是几十个高质量层级。

**建议 —— 三层内容模型（本项目的核心战略修正）**：

| 层级 | 数量（1.0 时） | 作者方式 | 成本/层 | 质量标准 |
|------|--------------|---------|---------|---------|
| **A 类：手工核心层** | 30-40 | 完全手工 + 定制 set piece | 20-40 人日 | 博物馆级，可被反复谈论 |
| **B 类：策展生成层** | 200-300 | 手工调优的 DNA 模板 × 程序化生成 + 人工抽查 | 2-5 人日 | 稳定、符合美学、有记忆点 |
| **C 类：野性生成层** | 数千 | 自动生成 + DNA 变异 | 0.1-0.5 人日 | "无尽回廊"的填充物，支撑数字叙事 |

- 发布时：**A(40) + B(250) + C(无限生成)** ≈ "探索不尽的数千层级"——数字叙事成立，且实际可交付。
- 后续每月"策展掉落"：把社区投票最高的 C 类提升为 B 类，形成内容飞轮。
- 营销口径从"4000 个手工层级"改为"**40 个手工奇迹 + 无尽生成的世界 + 社区共创**"——这反而更诚实、更有卖点。

### P0-2 ｜ 程序化生成与"后室恐怖"的审美张力

**现状**：设计书认为"层级 DNA 参数 + 模块组合"即可产出层级。但**恐怖感几乎全部来自"不合理的细节"**：一张写着莫名句子的纸条、一扇不该存在的门、一段毫无来由的走廊。纯参数生成的层级必然千篇一律、缺乏"被设计过的感觉"。

**建议 —— 引入 Set Piece（场景锚点）机制**：
- 每个层级 DNA 必须声明 1-5 个 `setPieces`（怪诞房间 / 墙上书写的文字 / 孤立的物品 / 尸体 / 壁画 / 祭坛），由手工作者提供，程序化层只负责把它们放置到合理位置。
- **铁律：程序化只生成"背景板"，恐怖由"前景的异常"负责。**
- 这也直接服务"故事家"玩家类型：set piece 是环境叙事的语法单元。

### P0-3 ｜ 核心循环缺"死亡与留存"闭环

**现状**：设计书写了"无目标、体验驱动、玩家自行定义意义"，但**没有定义玩家死亡后发生什么**。没有后果的生存游戏没有张力；没有留存机制，"探索日志"就只是本地记录，玩家没有回来的理由。

**建议**：
1. **永久死亡（permadeath）**：死亡 = 本轮结束，符合"后室吞噬你"的主题。
2. **跨轮持久"行记（Codex）"**：已发现层级、已收集文档、个人笔记、死亡记录全部持久化到档案库。**玩家输掉的是身体，赢得的是知识。**——这是"存在证明"主题的落点，也是 roguelite 式留存钩子。
3. 死亡结算页展示：本轮存活回合、发现层级数、死因、新解锁的 Codex 条目。

### P0-4 ｜ 理智（Sanity）系统只有概念，没有内容与数值

**现状**："理智过低触发幻觉、屏幕失真、声音扭曲"——一句带过。**理智是后室游戏区别于传统生存游戏的核心特色，它需要一套内容管线**，否则只是又一个被动的 debuff 条。

**建议（详见 GDD 3.2）**：
- **来源**：层级基础侵蚀 + 实体目击（LOS 内）+ 黑暗 + 声音压力事件 + set piece 惊吓。
- **恢复**：安全层环境回复、杏仁水、在光亮处休息。**恢复资源必须稀缺**，形成"理智经济"。
- **阶段与内容**：>50 平静 / 30-50 不安（轻度幻觉：错误的声响文字、地图上闪现的假实体）/ 15-30 恐惧（画面噪点、色彩失真、声音扭曲、假脚步声）/ <15 崩溃（随机失控行动、无法操作回合）。**每个阶段需要实际内容资产**——幻觉内容库（文字/音效/视觉层）是必须立项的内容品类。
- **结局**：理智归零 = "被后室同化"死亡，与 HP 归零（物理死亡）双结局。

### P0-5 ｜ 感知/潜行模型未定义

**现状**：设计书说"潜行、逃跑、利用环境、有限战斗"，但没有任何检测模型。没有模型就无法设计实体、无法平衡层级难度。

**建议（详见 GDD 3.3）——三通道感知模型**：
1. **光线通道**：暗处降低视觉范围；"笑魇（Smiler）"在黑暗中出现、在光照下遁形；"电灯（Duller）"相反——光照吸引。
2. **声音通道**：奔跑/战斗/开关门产生噪音，吸引听觉型实体（猎犬 Hound）；蹲行与静止降低噪音。
3. **视线通道**：直线视线 + 距离衰减；部分实体（Skin-stealer）仅在玩家"查看"时可见。
- 玩家工具：手电（光/电量）、蹲行、静止、投掷物（制造噪音引开敌人）。

### P0-6 ｜ "世界持久化"是隐藏的大功能，技术方案未覆盖

**现状**：设计书要求"探索日志记录连接方式""可回到安全层建基地"，但技术方案只有 PCG 与性能优化。**程序化层级必须有确定性（同一种子 → 同一层级），且玩家对层级的修改（搬动的物品、写的字、建的基地）必须持久化**，否则"回到 Level 1 的家"会变成"回到一个全新的 Level 1"——这摧毁整个探索日志叙事。

**建议**：
- 生成确定性：`层级ID + 轮次种子 → 布局`（mulberry32/PCG hash），存档只存种子与 delta（玩家修改）。
- 世界持久层：`(层级ID, 种子, delta记录)` 三元组存档结构；基地数据单独一份。
- 这直接影响原型验证——本次技术原型将直接实现确定性生成（见 `proto/`）。

### P0-7 ｜ UGC 编辑器是数月级工程，必须分阶段

**现状**：设计书把"内置层级编辑器 + 创意工坊深度整合"列为社区章节，未给阶段。

**建议（四阶段渐进）**：
1. **M1：只读社区内容导入**（创意工坊订阅 → 加载他人层级，服务器端校验安全）——成本低，先行验证 UGC 需求。
2. **M2：编辑器 v1**（DNA 参数化编辑 + 模块摆放 + set piece 放置 + 本地测试），先支持 B/C 类层级创作。
3. **M3：编辑器 v2**（脚本/触发器 + 自定义实体 + 多人协作审阅）。
4. **上线后：评分/策展/月度掉落**。
- 编辑器立项时间点：**M1 末**，用社区导入数据指导编辑器设计。

### P1-1 ｜ 音频设计被严重低估

**现状**：全项目 1 名音频设计师。但后室恐怖**70% 靠声音**——灯管嗡鸣、远处脚步、突然寂静。音效资产量（每层级环境底噪 + 突发音效 + 实体音效 + 理智幻觉层）远超 1 人 2 年的产能。

**建议**：
- 音频 1 人不变，但**走程序化音频管线**（Wwise 随机容器 + 程序化底噪合成），资产靠系统生成而非逐条手作。
- "突然的寂静"作为设计原语：静默切层（audio ducking）是后室最便宜的恐怖手段，写进层级 DNA（`soundscape` 字段）。
- 音频与理智系统联动：理智越低，音频层越扭曲（音高漂移、相位失真）。

### P1-2 ｜ 基地建设与"建筑师"玩家类型不对应

**现状**：设计书列出"建筑师"玩家类型（建基地、装饰空间），但核心玩法系统里**没有任何建造系统**。

**建议**：基地建设是完整的大系统（放置、结构、存档、多人冲突），**1.0 不立项**。对策：
- "建筑师"玩家在 1.0 的替代方案：**安全层固定房间可布置收藏品**（陈列架摆放收集品——简单、契合"收藏家"、成本极低）。
- 完整建造系统放到 DLC 或 UGC 编辑器能力中。

### P1-3 ｜ 多人/单人范围未声明

**现状**：全文未提。后室题材的多人诉求真实存在（联机逃出是热门品类），但多人会重构整个技术栈（状态同步、实体权威、世界一致性）与恐怖体验（恐怖在单人下才成立）。

**建议**：**明确 1.0 单人沉浸式体验**；将"氛围性联机（玩家可见但无法直接交流，如同幽灵）"作为长期愿景写入 roadmap，但不进 1.0 范围。市场沟通上也以"孤独感"为卖点，不与联机产品正面竞争。

### P2-1 ｜ IP 与合规：CC BY-SA 许可问题完全缺失 ⚠️

**现状**：设计书通篇基于 Fandom 版世界观（层级名、实体名、M.E.G.、杏仁水等均来自 Fandom wiki 条目）。

**事实**：
- Fandom wiki 内容采用 **CC BY-SA 3.0** 许可：允许商业衍生，但**必须署名，且衍生作品须以相同许可（BY-SA）发布**——对一款商业游戏意味着：署名页、以及"受 wiki 内容启发的玩家创作（UGC）"的许可处理策略。
- 概念层面："The Backrooms" 起源自 4chan 匿名帖，是一个公共 meme 概念；但**具体层级/实体/组织的设定与文本来自 wiki 条目**，逐条属于不同作者。
- 竞品现状：Steam 已有《Backrooms: Escape Together》《The Backrooms: Survival》《Roam The Backrooms》等，市场存在但未饱和，差异化空间在"Fandom 全量百科 + 美学还原"。

**建议**：
1. 立项即咨询**游戏法务**（中国或出海目的地），确认衍生范围与署名/许可策略。
2. 游戏内置"创作署名页"：列出主要参考的 wiki 条目与作者（CC BY-SA 要求）。
3. UGC 条款设计：玩家创作默认进入游戏的 CC BY-SA 生态（或采用双许可），法务确认后写入 EULA。
4. 名称策略：游戏名可用"Backrooms"（公共概念），但**避免直接使用 wiki 的整段原文文本**作为游戏内文档；游戏内文档一律原创改写。
5. 差异化定位：不做"又一个逃生恐怖"，做"**Fandom 百科的活体博物馆 + 无限生成的世界**"。

### P2-2 ｜ 里程碑节奏与 EA 策略缺失

**现状**：M0(12mo) → M1 Alpha(24mo) → M2 Beta(36mo) → M3 发布(48-60mo)，无 EA 节点、无预算测算。**5 年纯内包开发对一个 7-9 人团队是极高的现金流风险。**

**建议（详见 milestones.md）**：
- **EA 提前**：M1 结束（18-24 个月）即上 EA，以 100-150 层级 + 核心系统发布。EA 既是收入来源，也是社区内容输入点。
- 预算粗算：团队 8 人 × 4 年，国内成本约 800-1200 万 RMB（不含发布/法务）；EA 收入 + 发行商可覆盖 60-80%。
- 发布目标（1.0）：A(40) + B(250) + C(无限) + 社区导入内容。

### P2-3 ｜ 4000 层的 QA 与 Telemetry

**现状**：无 QA 策略。程序化生成意味着**每个玩家遇到的层级都可能是"新代码路径"**。

**建议**：
- 自动化冒烟测试：CI 中批量生成 1000 个种子 × 每层级，验证可达性（BFS 出生点→出口）、无死锁、实体密度合法。
- 发布后 Telemetry：层级卡死率、实体卡墙率、掉入虚空率 → 反馈到 DNA 模板修复。
- 本次技术原型将内置这一冒烟测试逻辑（见 `proto/test.js`）。

## 四、结论

设计书的**产品定位与世界观理解是顶级的**，问题全部出在"从愿景到工程"的转化层。本评审不否定任何核心理念，而是把"4000 层级"从**营销数字**修正为**三层内容模型 + 无尽生成**的可执行目标，并为缺失的系统闭环（死亡留存、感知模型、理智内容、世界持久化）补上规格。修订后的完整设计见 `gdd-v0.2.md`。
